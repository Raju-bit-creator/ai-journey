# Testing & verification

A passing build is not verification. Prove the behavior by exercising it.

## What to run

| You changed | Run |
|---|---|
| `backend/` | `npm run build` · `npm run lint` · `npm test` · `npm run test:e2e` (from `backend/`; containers must be up: `docker compose up -d`) |
| `src/` (frontend) | `npx tsc --noEmit` · `npm run lint` · a browser check of the affected page |
| `python/` | `source venv/bin/activate && pytest -v` (run `python train.py` first if `model/iris_classifier.joblib` is missing) |
| `llm/` | `npx tsc --noEmit`, then run the CLI once |
| Docker/compose | build the image, start it, and hit a real data endpoint — not just `/health` |

The frontend has no unit-test framework. Its verification is typecheck + lint + a real browser run.

## Backend (Vitest, ESM)

- **Unit** — `src/**/*.spec.ts`, `npm test`. Mock the repository with `{ provide: getRepositoryToken(Entity), useValue: repo }` and Redis with `{ provide: REDIS_CLIENT, useValue: redis }` using `vi.fn()`. Globals (`describe/it/expect/vi`) are enabled — no imports needed. Mock only what the unit touches.
- **E2E** — `test/*.e2e-spec.ts`, `npm run test:e2e`. Boots the real `AppModule` against the **real dev Postgres/Redis**. Therefore: use unique data (`e2e_<label>_${Date.now()}@example.com`), track what you create, and delete it in `afterAll`. Verify nothing leaked (`SELECT ... WHERE email LIKE 'e2e_%'`). Re-apply `useGlobalPipes(new ValidationPipe({ whitelist: true, transform: true }))` in the test app — `main.ts` isn't run.
- Any new authorization rule gets both: a unit test on the service and an e2e test with two users proving the stranger gets 403.
- **Prove a test can fail.** For security-sensitive logic, temporarily break the code (e.g. comment out `assertOwnership`) and confirm the tests go red, then revert.
- A single "socket hang up" with 5/6 passing is usually transient; re-run before debugging. A consistent assertion mismatch is a real bug.

## Python (pytest)

`pytest.ini` sets `pythonpath = .`, so imports are `from app.main import app`. Tests use FastAPI's `TestClient`. The model file is gitignored and must be generated by `python train.py`.

## Browser verification (Playwright)

Playwright is not a project dependency. Install it in a scratch directory (`npm i playwright`); browsers are cached under `~/Library/Caches/ms-playwright`. Pitfalls that create **false failures**:

- `page.click('button[type="submit"]')` clicks the **first DOM match** — after login that's the header "Log out" button, not your form's submit. Scope it: `page.locator('form:has(#name) button[type="submit"]').click()`.
- `page.waitForURL(pattern)` resolves immediately if the URL already matches (e.g. a logout that redirects back to the same page). Wait for a DOM change instead (`waitForSelector('a:has-text("Log in")')`).
- Server Actions that call Gemini can take 30s+ (or minutes when throttled). Use generous timeouts and catch timeouts instead of letting the browser die — chat state is in-memory and lost when the page closes.
- Register a fresh user per run with a unique email, and delete test users/products afterward.

## LLM-backed features

- Test retrieval (`embed` → `topK`) and tool `execute` functions **directly** — they're free and deterministic.
- Every model call spends scarce quota (20/day free). Get the logic right with one or two real calls; don't loop. If something hangs, suspect `429 RESOURCE_EXHAUSTED` in the server log before suspecting a code bug.

## Hygiene

- Clean up test data (products, users, Redis `session:*` leftovers) and stop any dev servers you started.
- Before starting a server, check who holds the port: `lsof -iTCP:<port> -sTCP:LISTEN -P`. Editor-managed servers may hold ports with stale env — restart them rather than debugging phantom failures.
- Report what you verified **and what you didn't**.
